# Tenchi framework audit — 2026-11-07 (v0.19.1, HEAD 935c237)

A follow-up deep audit of the framework, five releases after the
[2026-08-22 audit](AUDIT-2026-08-22.md) (v0.14.0). It re-checks that audit's
dispositions at HEAD and hunts for new defects with the same lens: (1) make it
easy for coding agents and humans to **build** correct backends, (2) make it
easy for machines to **consume** them, (3) does the verification/receipt
machinery stop an agent from faking "done" within its stated limits, and, added
this cycle, (4) is every stated guarantee in `AGENTS.md`, the README, the docs,
and the package metadata actually true.

Method: six parallel deep reviews (core HTTP boundary; operational/durability
surface; machine-consumption surface; **verification/receipt machinery**; CLI,
scaffold, generators, doctor, and the coding-agent MCP server; examples, docs,
packaging, CI, dependencies, and the benchmark harness). Each read source and
tests, wrote executable probes, and reproduced suspected bugs by execution.
**confirmed** = reproduced with running code; **suspicion** = traced in code but
not executed. Every high finding and the load-bearing medium findings were then
**independently re-reproduced from scratch by the author of this report** with
new probes and, where the finding defeats a defense, a control run showing the
defense working first (see [Validation](#validation)).

Dispositions from the previous audit were respected: the in-process pytest
receipt's forgeability by project-owned code in the pytest interpreter is an
accepted, disclosed limitation and is not re-reported as such. What **is**
reported is where the behavior goes beyond that disclosure.

Everything the repo gates on is green at HEAD:

  0 errors, **1441 tests passing, 7 skipped** (up from 1196; the skips are
  POSIX permission cases that cannot run as root)
- `examples/taskboard`: 87 tests passing, Pyright clean, `tenchi doctor` clean,

## Verdict in one paragraph

The framework is in better shape than at any previous audit. **Every item the
2026-08-22 follow-up marked Fixed holds at HEAD under re-execution**, the
examples and every tutorial are honest to the code, the compatibility analyzer
is directionally correct across a 49-case battery, and the boundary hardening
(size limits, header funnels, redaction, no late success) survived a real
uvicorn harness with pipelined raw-socket requests. Two findings nonetheless
defeat stated guarantees. First, the **receipt's source identity can be made
indistinguishable from a pristine checkout while hidden project code forges the
evidence**: `.git/info/exclude` and repo-local `core.excludesFile` are honored
by the digest's `--exclude-standard` listing, so the previous audit's accepted
limitation ("visible in the diff, inspect the conftest") is no longer the whole
story — the forgery can be invisible in the commit, the receipt, and a
reviewer's clone. Second, the **published dependency lower bounds are false**
(`pydantic>=2.7`, `typing-extensions>=4.10` do not import or compose; the real
floors are 2.10 and 4.13) and the CI job that `AGENTS.md` says makes those
claims executable cannot see it because the dev group pulls the floors back up.
Around these sit a familiar set of medium defects: `check` steps that a
project-owned package can replace outright, tracked symlinks whose content
escapes the digest, two composition-time promises still missed at the HTTP
boundary, a `Retry-After` gap on code-selected retries, a payload leak at the
tool boundary, an OpenAPI generation failure with wrong advice, a conformance
suite that certifies a lease-anchored store, a silently lossy job message, and
a teaching hook that 500s on non-ASCII credentials. None is architectural, and
the two highs are each a small, well-localized fix.

## High-severity findings

### H1. Receipt source identity cannot see project code hidden by `.git/info/exclude` or repo-local `core.excludesFile` (confirmed)

**Claim.** `AGENTS.md` ("CLI expectations"): the receipt "records the current
HEAD, dirty state, and a canonical digest of tracked and nonignored untracked
paths below the application root", and the accepted H1 disposition from the
previous audit relies on the forging code being *present and reviewable*: "use
an external evaluator with withheld tests when the code producer is
adversarial, and preserve the accepted plan ID outside the edited worktree".

**Behavior.** `_source_identity.py:124-135` lists paths with
`git ls-files --cached --others --exclude-standard`, and `:138-148` reads
`git status --porcelain`. Both honor `.git/info/exclude` and a repo-local
`core.excludesFile` in the untracked `.git/config`. `_git.py:40-50` strips the
global and system Git configuration environment but not repo-local
configuration. A `conftest.py` that skips the planned target and writes the
evidence file from `atexit`, once listed in `.git/info/exclude`, produces a
receipt that is **byte-identical to an honest one**: same HEAD, same digest,
`(clean)`, `ok: true`, exit 0 — while the planned test fails when run
directly. The same holds through `git config core.excludesFile`.

**Impact.** The disclosed mitigation cannot be applied because there is nothing
to inspect: the forgery is in neither the commit nor the receipt, and
`git status`/`git diff` in a reviewer's clone show nothing. This upgrades the
accepted limitation from "visible" to "invisible" and defeats the receipt's
stated purpose of binding evidence to Git-visible source.

**Fix.** List untracked paths with tree-visible rules only
(`git ls-files --others --exclude-per-directory=.gitignore`) and either fold the
delta against `--exclude-standard` into the digest and `dirty`, or fail the
`source` stage when the two listings differ (at minimum for `conftest.py`,
`pytest.ini`, `tox.ini`, `setup.cfg`, `pyproject.toml`, `tenchi.toml`,
`*.pth`, `sitecustomize.py`). Add a regression test beside
`test_source_identity_excludes_ignored_paths`.

### H2. Published dependency lower bounds are false, and the CI job that claims to prove them cannot see it (confirmed)

**Claim.** `pyproject.toml:35-42` publishes `pydantic>=2.7`,
`typing-extensions>=4.10`, `jsonschema>=4.23`, `referencing>=0.28.4`;
`AGENTS.md` ("Versioning and releases"): "The Python 3.12 `lowest-direct` CI
job makes those published compatibility claims executable."

**Behavior.** At the exact floors `import tenchi` fails: `evaluations.py:47`
imports `TypeForm` from `typing_extensions`, which exists from 4.13.0. With
`pydantic` 2.7–2.9, route binding fails on every app
(`routes.py:411,450`, `server.py:637`, `client.py:1631-1633` use
`TypeAdapter.pydantic_complete`, added in 2.10) and `_change_plans.py:26`
cannot build a schema for its PEP 695 `type` alias. Pydantic 2.10.0 is the
first version that works. The `minimum-dependencies` job in `ci.yml` resolves
with `UV_RESOLUTION=lowest-direct`, which lowers only direct requirements; the
dev group's `mcp>=2`, `httpx2`, and `opentelemetry-sdk` pull pydantic to 2.12,
typing-extensions to 4.14, jsonschema to 4.26, and referencing to 0.37. The job
executes none of the four claims; it only exercises `httpx 0.27`,
`starlette 0.37`, and `aiosqlite 0.20`.

**Impact.** A stated compatibility guarantee is defeated; a downstream resolver
can legitimately select a combination that fails at import or composition.

**Fix.** Raise the floors to what the code uses (`pydantic>=2.10`,
`typing-extensions>=4.13`; re-derive jsonschema/referencing the same way) and
make the lowest-bounds job install only runtime floors plus the test tools
(`uv sync --no-group dev` with an explicit pytest/pytest-asyncio install, or a
`uv pip install` matrix) so it can fail for the right reason.

## Medium-severity findings

### Verification and receipt machinery

- **Every `check` step can be replaced by a project-owned package (confirmed).**
  `_checks.py:465-467` runs tools as `[sys.executable, "-m", module, ...]` with
  `cwd=root` (`:409-432`) and no `-P`/`PYTHONSAFEPATH`, so the application root
  is `sys.path[0]`. Committed `ruff/__main__.py` and `pyright/__main__.py` that
  exit 0 make `ruff format`, `ruff`, and `pyright` vacuous while `verify`
  reports them passed; a `pytest/__main__.py` that writes an all-passed
  evidence file produces `test_execution: passed` with provenance
  `project_pytest_process` although **no pytest process ever ran**; a `tenchi/`
  package can shadow `tenchi.cli` for the doctor and OpenAPI steps. `doctor`
  does not object to the top-level packages. This exceeds the disclosure, which
  describes code running *inside* the pytest interpreter, not the absence of
  the tools. Visible in the commit, hence medium; combined with H1 it is
  invisible. *Fix (verified feasible):* run every step with `-P` /
  `PYTHONSAFEPATH=1`; the generated app's pytest, doctor, ruff, pyright, and
  `openapi --check` all behave identically under `-P`.
- **Tracked symlinks let verification run code whose content is outside the
  digest (confirmed).** `_source_identity.py:291-306` hashes a symlink's mode
  and target string only; doctor rejects symlinks only under `app/`. A
  committed `conftest.py -> ../outside_conftest.py` runs the forging conftest
  from outside the root; editing the outside file leaves the digest unchanged
  and the receipt `dirty: false`. *Fix:* fail the `source` stage, or set
  `dirty`, for any symlink whose real path leaves the application root.

### Core HTTP boundary

- **Path converters compose against an incompatible params type and then 422
  on every request (confirmed).** `contract()` accepts Starlette's
  `{name:converter}` syntax (`contracts.py:68-70, 785-791`);
  `routes._check_params_match_path` (`routes.py:397-440`) compares field
  *names* only, although its own docstring promises that a route which "would
  422 on every single request" fails at import. Starlette converts the
  segment, then Tenchi validates the converted value (`server.py:1250-1253`):
  `/int/{id:int}` with `id: str`, `/uuid/{id:uuid}` with `id: str`, and
  `/float/{id:float}` with `id: int` all compose and all 422 with
  `x-tenchi-error-source: framework`. OpenAPI publishes the string parameter
  the runtime never accepts, and the typed client sends `"5"` and receives a
  framework 422. *Fix:* map each converter to its output type and require the
  field's validation schema to accept it (or reject non-`str`/`path`
  converters unless the JSON type matches), or validate `params` from the raw
  segments.
- **Request validation accepts non-finite JSON numbers the published schema
  cannot express; the result is a framework 500 or a silent `null`
  (confirmed).** `server.py:1279` calls `validate_json` with pydantic-core
  defaults, which accept the non-RFC-8259 literals `NaN`/`Infinity` and
  overflow `1e400` to `inf` for `float` fields that OpenAPI publishes as
  `type: number`. The use case runs (and may persist) the value; on the way out
  `_validated_payload` (`server.py:929-936`) serializes NaN as `null`, fails the
  serialization schema, and returns **500 framework** for a client-input
  problem. For `float | None` the NaN silently becomes `null`; `?score=nan` is
  accepted on the query path. The typed client cannot produce this (it
  serializes NaN as `null`, which the server correctly 422s), so only raw and
  other-language clients hit it — the machine consumers the framework targets.
  *Fix:* reject non-finite input at the boundary (a cheap pre-scan with
  `parse_constant` when the bytes contain those tokens, or `allow_inf_nan=False`
  where Pydantic exposes it) on body, query, header, and path validation, and
  mirror it in the client preflight.

### Machine-consumption surface

- **Code-selected retries ignore the server's `Retry-After` when the client's
  `ErrorDef` does not declare that header (confirmed).** `client.py:578-586`
  reads the raw response header only on the status-selected path; the
  code-selected path reads `_app_error_retry_after(exc)` (`:1316-1324`), which
  comes from `AppError.headers`, filled at `:1172-1182` only from names in
  `definition.headers`. A `503 BUSY` with `Retry-After: 60` against
  `retry_policy(retry_on=("BUSY",), max_delay_seconds=0.5)` retries after
  0.05 s. This contradicts `AGENTS.md` ("treat a valid `Retry-After` as a
  minimum wait ... never clamp the server's delay downward"), the
  `retry_policy()` docstring, and `client.mdx`, and it is the path the
  Unreleased changelog entry is about. *Fix:* use `attempt.retry_after_header`
  on both paths; add a regression test for the undeclared-header case.
- **`ToolRunner.call()` raises a raw Pydantic `ValidationError` carrying the
  rejected input, unlike jobs, tasks, and `execute()` (confirmed).**
  `tools.py:507-508` re-raises `ValidationError`; the siblings were given
  payload-safe `JobPayloadError`/`TaskInputError`/`ExecutionInputError` last
  cycle. With `token: int` and input `"sk-live-SECRET-123"`, `str(exc)` and
  `exc.errors()` both contain the secret; the MCP adapter redacts it, but the
  tool boundary is *the* model-supplied-input boundary and any other adapter
  following `tools.mdx` leaks it into logs or transcripts. *Fix:* a
  `ToolInputError(name, issues)` mirroring the siblings.
- **One model used for both request validation and response serialization
  fails OpenAPI generation with wrong advice when its two schemas differ
  (confirmed).** `openapi.py:849-872` merges `$defs` by model name across modes
  and raises `conflicting schemas for component 'X'; rename one of the models`
  (`:867-870`). A nested model with a `@computed_field`, or a
  `@field_serializer` that changes the JSON type (`Decimal -> str`), triggers
  it; the app composes, serves, and round-trips fine, but `openapi_schema()` —
  and so `tenchi openapi`, `check`, `verify`, and `openapi_route()` — fail, and
  renaming cannot help. *Fix:* one `models_json_schema` pass with
  `-Input`/`-Output` disambiguation when the two modes differ; split the error
  message.
- **A shared `Client` replays dependency-set cookies across calls (confirmed
  mechanism; impact usage-dependent).** `client.py:400-404` uses httpx's
  default persistent cookie jar; nothing disables or documents it, while
  `client.mdx` recommends one long-lived `Client` with per-call `headers=`
  credentials. A `Set-Cookie` from one principal's call is replayed on the next
  principal's call. *Fix:* document, and offer a non-persisting jar or an
  explicit `cookies=` option.

### Operational and durability surface

- **`verify_idempotency_store` certifies an adapter whose completed replay
  expires with the reservation lease (confirmed).** The only numeric-TTL probe,
  `completed_expiration` (`_idempotency_store_conformance.py:283-345`), uses
  `reservation_ttl == completed_ttl == 10` and completes with **no clock
  advance** between reserve and complete, so the correct expiry
  (`completed_at + completed_ttl`), a buggy `reserved_at + completed_ttl`, and a
  buggy "forgot to extend the lease" `reservation_expires_at` all coincide. The
  mid-TTL survival probe added last cycle (`:308-320`) is anchored to the same
  instant. A store with the lease-anchored bug is certified and, in a
  production-shaped call (`reservation_ttl=300`, `completed_ttl=86400`,
  operation runs 200 s), **re-executes a replay 150 s after completion** —
  the class of defect the suite exists to catch and the remaining hole in last
  cycle's "premature expiry" fix. *Fix:* use distinct TTLs, advance the clock
  between reserve and complete, and assert survival past the lease and until
  `completed_ttl` after completion.
- **`job_message()` certifies a lossy serialization (confirmed).**
  `_serialized_job_payload` (`jobs.py:205-227`) dumps with `round_trip=True`,
  validates against the published schema, and strictly revalidates, but never
  compares the round-tripped value with the validated input — the comparison
  `run_idempotently()` does perform via `same_python_value`
  (`idempotency.py:488-492`). A `SecretStr` field on a job request (an easy
  mistake when an agent reuses an HTTP request type) enqueues ten asterisks;
  a formatting `field_serializer` that keeps the shape but truncates the value
  is accepted. `jobs.mdx:67-69` promises a `JobBindingError` for serializers
  that emit "a different wire shape", which is true and insufficient. *Fix:*
  `same_python_value(validated, revalidated)` after strict revalidation, raising
  `JobBindingError` on mismatch.

### Examples, docs, packaging

- **The todos API-key hook returns a framework 500 for a non-ASCII `X-Api-Key`
  (confirmed).** `examples/todos/app/server/hooks.py:29` calls
  `hmac.compare_digest` on `str`, which raises `TypeError` for non-ASCII;
  Starlette decodes header bytes as Latin-1, so any byte ≥ 0x80 reaches it. Not
  a bypass, but the teaching hook (commented "Constant-time comparison") turns
  malformed credentials into 500s plus tracebacks, and it is what users copy.
  `TODOS_API_KEY` appears on no docs page. *Fix:* compare encoded bytes.
- **`CHANGELOG.md [Unreleased]` records public additions under "Fixed"
  (confirmed, documentation).** `CHANGELOG.md:19-25` lists new CLI flags
  (`tools --diff-ref --allow-missing-baseline`,
  `verify --allow-missing-tool-baseline`) and new coding-agent MCP inputs
  (`agent_protocol_v13_snapshot.json` gained `allow_missing_baseline` /
  `allow_missing_tool_baseline`) under **Fixed**. `tests/api_snapshot.txt` is
  unchanged since 0.19.0, so 0.19.1 as a patch is defensible, but these are
  Keep-a-Changelog **Added** entries and the v13 additive protocol update is
  easy to miss on a declared release surface.

### CLI, scaffold, generators, doctor, coding-agent MCP

- **Doctor has no rules for `app/__init__.py`, `app/features/__init__.py`, or
  any extra top-level package such as `app/lib/` (confirmed).**
  `_classify_module` (`doctor.py:675-721`) returns `None` for `("app",)`,
  `("app", "features")`, and `("app", "<other>", ...)`, and
  `_placement_findings` (`doctor.py:403-425`) flags only a two-part non-init
  module (`app/helpers.py`) or an unrecognized module inside a feature. A
  whole package outside the four canonical ones, and the two package
  initializers that run on every `app.*` import, escape every dependency rule:
  `app/__init__.py` and `app/lib/__init__.py` importing
  `app.infra.memory_todo_repository` and `app.server.asgi` leave `doctor: no
  problems found`, while the same import in `app/features/todos/__init__.py`
  is `TENCHI_DOCTOR_FORBIDDEN_IMPORT`. `AGENTS.md` says "Dependency direction
  is enforced by `tenchi doctor`" and `verify`'s architecture stage relies on
  it; an `app/__init__.py` that imports the composition root makes the whole
  feature layer depend on it with `map` (0 diagnostics), `check`, and `verify`
  green. Same class as last cycle's fixed feature-`__init__` and top-level
  `app/*.py` blind spots, one level up. *Fix:* flag any `app/<pkg>/...` whose
  first segment is not `features|shared|infra|server`, and give `("app",)` and
  `("app", "features")` the `shared` rule set.
- **`make feature` and `make use-case` write through symlinked parent
  directories to paths outside the application root (confirmed).**
  `make_feature_result` checks only `feature_root.exists()`
  (`_cli_operations.py:139-151`), `make_use_case_result` only the two output
  files (`:296-308`), and `_write_files_transactionally` (`:673-699`) then
  `mkdir(parents=True)` and opens with `"x"`, both following symlinks. With
  `app/features/invoices/use_cases -> /tmp/outside`, `make use-case invoices
  escaped` reports `Created app/features/invoices/use_cases/escaped.py` and
  the file lands outside the root; the same for a symlinked `app/features`.
  `make capability tools` refuses symlink parents (verified) and doctor rejects
  symlinks below `app/`, so this is a consistency gap in the two generators
  agents use most. *Fix:* reuse the capability generator's unsafe-path check in
  `_write_files_transactionally`.

## Low-severity findings (condensed)

**Verification.** `--base-ref HEAD` is a silent equality check: a breaking
rename reports `compatible, changes: []` with `baseline.commit ==
source.head_commit` and no flag (`_verify_operations.py:455-465`); a
`baseline.relationship` field would make this explicit. Ambiguous short names
resolve to the tag over the branch (`_openapi_operations.py:474-497`) with Git's
warning on stderr only. A symlinked `tenchi.toml -> policy/weak.toml` reads the
baseline from `<commit>:policy/weak.toml` and labels the result "policy added"
instead of "removed" (still fails closed). A `.git` file with `core.worktree`
elsewhere yields a `source` block mixing another repository's HEAD with the
cwd's digest (`verify` still fails on snapshot resolution). The incomplete
marker is an exact substring, so `#  tenchi: incomplete` (two spaces) passes
`incomplete_marker_removed` and doctor (`_verify_operations.py:917-932`).
Receipts carry raw failure output: a failing test that prints a payload or an
environment value puts it into `check.steps[].stdout/stderr` of the `--json`
receipt and the MCP result (`_checks.py:378-390`) — not a stated promise, but
worth a redaction pass or a docs line. `PYTHONPATH` is cleared only for the
pytest child (as claimed); a `sitecustomize.py` on it runs in the ruff,
pyright, doctor, and OpenAPI children. Change plans are content-addressed only;
a retargeted plan with a recomputed `plan_id` loads (disclosed).

**HTTP boundary.** A passthrough `FileResponse` 500s at request time with
`undeclared headers: ['accept-ranges']` (and `RedirectResponse` with
`['location']`) until declared, after which `FileResponse` adds
`last-modified` and `etag` inside `__call__`, past Tenchi's check
(`server.py:1093-1102`); the docs' file/redirect recipe needs either send-time
validation or a statement of the limit. Passthrough bodies are never validated
even when materialized (`server.py:1038-1104`), which overstates the
`responses.mdx` callout. A health check that raises `CancelledError` aborts the
request with no response instead of a 503 (`health.py:487-491`; use
`current_task().cancelling()`). `execute()` performs no result validation,
so the value HTTP rolls back as a 500 is returned and committed by `execute()`
(`execution.py:256-262`); `AGENTS.md` says it runs use cases "with the server's
boundary guarantees". A declared `AppError` raised inside an
`asyncio.TaskGroup` surfaces as an `ExceptionGroup` and becomes a framework 500
with the observer reporting `failed` (`server.py:1487`, `execution.py:131`).
`open_http` raises middleware exceptions in-process that are 500 envelopes under
uvicorn (`testing.py:142` uses `raise_app_exceptions=True`), and the comment at

## Priorities

1. **Make the receipt see what pytest sees (H1).** Enumerate untracked paths
   with tree-visible ignore rules only, fail or dirty the `source` stage on any
   difference from `--exclude-standard`, and fail it for symlinks that leave
   the root. This restores the previous audit's accepted limitation to
   "visible", which is the premise its mitigation depends on.
2. **Run every `check` step with `-P`.** One flag closes the tool-shadowing
   class and makes `project_pytest_process` provenance mean a pytest process
   ran. Consider a doctor finding for top-level packages named after tools.
3. **Publish true floors (H2)** and rebuild the lowest-bounds job so the dev
   group cannot mask them.
4. **Finish the two composition-time promises** at the HTTP boundary:
   converter/type agreement in `route()`, and non-finite JSON rejected at every
   input boundary (mirrored in the client).
5. **Close the symmetric gaps**: `Retry-After` on code-selected retries,
   `ToolInputError`, value-preserving `job_message()`, the completed-TTL
   conformance probe, the dual-mode OpenAPI component merge, doctor rules for
   `app/__init__.py` and non-canonical top-level packages, and the
   unsafe-path check in the feature and use-case generators.
6. **Tidy the teaching and release surfaces**: byte-compare in the todos API-key
   hook, move the Unreleased additions to "Added", move example health probes
   out of the DB request context, prune the sdist, add `--version`, refresh the
   locks for the certifi and OpenTelemetry advisories, and bring `AGENTS.md`'s
   module inventory back in line.

## Strengths worth preserving

- **The previous audit's Fixed items are genuinely closed** and held under
  independent re-execution; the test count rose 1196 → 1441.
- **Boundary hardening is defense-grade under a real server**: with pipelined
  raw-socket requests, early returns (413 by declared length, 413 by counted
  stream, 415 with a body, unread bodies, HEAD on GET) neither desync keep-alive
  nor let an unread body be parsed as a request; 100 000-deep JSON is a clean
  422; inbound request ids are sanitized before reflection; "no late success"
  holds for swallowed cancellation, slow hooks, and slow commits.
- **Receipt integrity is strong everywhere the gap is not Git's own ignore
  machinery**: `GIT_*` environment stripping, `git replace` neutralized,
  abs/`..`/symlink *content* escape resistance, persistent-change rechecks,
  fail-closed policy comparison across every malformation tried, and a
  49-case compatibility battery with correct direction and `unknown` for
  `anyOf`/`allOf`/`not`/`readOnly`.
- **Change-plan structural rules behave exactly as documented**: skipped,
  factory-bound, decorator-wrapped, uncollected, and aliased targets each fail
  for the documented reason.
- **`run_idempotently()` is fail-closed on every path driven** (AppError,
  invalid result, task cancel, `asyncio.timeout`, a failing `abandon`), and the
  taskboard SQLite adapters are careful consumers (writer-lock-before-clock,
  token-fenced complete/abandon, payload-free dead-letter logging, no double
  processing under three concurrent workers).
- **Docs are honest to the code**: every snippet import and keyword resolves,
  reference signatures match `inspect.signature` exactly, the CLI reference
  matches `--help`, and every tutorial runs verbatim to a green receipt.
- **The CLI's structured-result contract is airtight**: across 65+ `--json`
  invocations spanning success, failure, and hostile environments (import
  errors, non-UTF-8 source, symlinked and unicode roots, subdirectories,
  outside an app) exactly one JSON object reached stdout, stderr stayed empty,
  and no application exception text entered an `operation_error`. The
  coding-agent MCP server wrote nothing during inspection and preview (tree
  hash unchanged), rejected every path-escape variant but the NUL byte, kept
  stdout to JSON-RPC even against fd-level writes, killed the pytest subprocess
  on cancellation with no orphan, and matched the v13 protocol snapshot for all
  17 tools. Ten concurrent `make use-case` runs produced one winner and nine
  clean refusals.
- **The application MCP adapter does what it says**: authenticated discovery
  and invocation, per-principal visibility rechecks, destructive-tool approval
  gating, redacted inputs and exceptions, `isError`, SSE rejection, and the
  4 MiB cap, all verified by execution.
