## Start with a working application

```shell
uvx tenchi new my_app
cd my_app
uv sync
uv run tenchi check
```

The generated application is runnable immediately. Its checks cover formatting,
typing, tests, architecture, and the versioned HTTP, job, tool, and evaluation
boundaries.

## The development loop

Tenchi is designed around a short loop that people, coding agents, and CI can
all follow:

1. **Inspect** the application graph and the contract you intend to change.
2. **Preview** framework-shaped files before writing them.
3. **Implement** behavior in ordinary Python and keep dependency wiring
   explicit.
4. **Check** typing, tests, architecture, and snapshot drift in one command.
5. **Verify** the finished tree against an immutable Git baseline.

```shell
uv run tenchi map --feature todos
uv run tenchi make use-case todos complete_todo --dry-run --json
uv run tenchi check
uv run tenchi verify --base-ref origin/main
```

A successful verification receipt identifies the source it checked and reports
the enforced architecture, test, OpenAPI, durable-message, application-tool,
and evaluation-policy evidence. It does not claim that weak tests prove the
business requirement; it makes the available evidence explicit and difficult
to skip accidentally.

## One use case, several entrypoints

Application behavior stays in a plain async function:

```python
async def create_todo(
    request: CreateTodo,
    context: AppContext,
) -> Todo:
    return await context.todos.create(title=request.title)
```

Bind that function to the boundaries your application needs:

| Caller | Tenchi boundary |
| --- | --- |
| HTTP client | A `Contract` bound with `route()` |
| Queue consumer | A durable `Job` bound at server composition |
| Operator | A named, validated operational `Task` |
| AI runtime | A typed application `Tool`, optionally served over MCP |
| Python code | `execute()` with the same context-scoping rules |

The use case does not receive a Starlette request, queue message, MCP request,
or database connection. Identity and ports arrive through the application
context, so behavior remains testable and reusable without hiding composition.

## What Tenchi verifies

- **Boundary correctness:** requests, responses, headers, errors, and tool or
  job payloads are validated against their declarations.
- **Composition correctness:** incompatible signatures, duplicate routes, and
  invalid declarations fail before the first request.
- **Architecture:** `tenchi doctor` checks dependency direction and required
  composition points.
- **Compatibility:** OpenAPI, durable job messages, application tools, and AI
  evaluation policy can be compared with a historical release.
- **Completion evidence:** `tenchi verify` combines the repository's required
  checks and compatibility reports into one source-bound result.

Tenchi deliberately does not choose an ORM, queue, scheduler, model provider,
agent loop, or deployment platform. It defines where those choices connect to
application behavior and what can be checked at each boundary. Read [Choose the
right framework](/comparisons) for the tradeoffs.
